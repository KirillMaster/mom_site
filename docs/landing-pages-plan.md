# План посадочных страниц — angelamoiseenko.ru

## 1. Список страниц

URL — транслит без дефисов-аббревиатур, кириллица-подобная латинская транслитерация (`kupit-kartinu`, не `buy-painting`): для Яндекса транслитерированный URL исторически даёт небольшой плюс к релевантности сниппета (совпадение с запросом визуально в адресе), и это соответствует уже принятому в проекте паттерну доменных имён на латинице (`angelamoiseenko.ru`). Английские URL здесь неуместны — аудитория и запросы полностью русскоязычные, английский URL не даёт никакого преимущества ни для Яндекса, ни для Google.ru, а транслит совпадает с тем, как пользователи иногда копируют кириллические запросы в адресную строку.

## 2. Структура блоков коммерческой посадочной

Единый каркас для всех четырёх (с вариациями по типу страницы), сверху вниз:

1. **Hero**: H1, короткий подзаголовок с УТП (импрессионизм, 20+ лет, Крым), кнопка CTA "Оставить заявку" / "Подобрать картину", ведущая к форме в конце страницы (якорь `#order-form`).
2. **Доверие**: строка/блок с образованием, годами опыта, участием в выставках, числом проданных/находящихся в наличии работ (286 работ в галерее — конкретная цифра работает лучше общих фраз). Данные берутся из тех же полей, что уже редактируются в `/admin/pages` для `about` (`biography`, `additional_biography`), но не дублируются копипастом — см. п.3, поле `TrustBlockRef`.
3. **Примеры работ по теме страницы**: 6-9 карточек работ, отфильтрованных по `CategoryId` (для `/natyurmorty`, `/peyzazhi`) или по тегу "портрет"/`IsForSale` для `/kupit-kartinu` — переиспользуется `ArtworkDto` и компонент карточки из галереи, каждая карточка ведёт на `/gallery?artwork=N`.
4. **Цены/вилка**: диапазон цен по типу работ (берётся из реального разброса `Artwork.Price` в соответствующей категории на бэкенде, не хардкодится) — блок вида "От X до Y ₽ в зависимости от размера и сложности".
5. **Процесс заказа** (обязателен на `/zakazat-portret`, опционален на остальных): нумерованные этапы — 1) заявка с фото/референсом, 2) согласование эскиза и цены, 3) предоплата 30-50%, 4) написание (срок в неделях), 5) фото готовой работы на согласование, 6) доставка/самовывоз, окончательная оплата. Явно указать типовой срок (например, 2-4 недели) и размер предоплаты — отсутствие этой информации на текущем сайте создаёт основной барьер к заявке.
6. **Отзывы**: если реальных отзывов пока нет как отдельной сущности (в проекте таблица `Reviews` уже удалена миграцией `RemoveReviewsTable` — значит, раздел отзывов сознательно не поддерживается как отдельная сущность) — заменить блоком "Мои работы в интерьерах клиентов" с фотографиями из S3, либо коротким текстовым блоком благодарностей через `LandingPage.ReviewsHtml` (см. п.3), не поднимать таблицу Reviews заново без явного запроса.
7. **FAQ**: 4-6 вопросов, специфичных под тип страницы (для портрета: "Можно ли по нечёткому фото?", "Что если не понравится результат?"; для картин: "Как происходит доставка?", "Можно ли увидеть картину вживую перед покупкой?").
8. **Форма заявки** (`id="order-form"`): переиспользует существующий `POST /api/public/contact-message` и `ContactMessageDto` (в нём уже есть `UtmSource`, `UtmMedium`, `UtmCampaign` — см. `backend/MomSite.API/Controllers/PublicController.cs`), плюс скрытое поле `Subject`, преднастроенное значением типа страницы ("Заявка: купить картину" / "Заявка: заказать портрет"), чтобы в письме/Telegram-уведомлении сразу было видно источник лида. UTM считываются из query-параметров страницы при заходе (стандартный `useSearchParams` в клиентском компоненте формы) и прокидываются в скрытые поля формы.

## 3. Техническая реализация без хардкода

Расширять `PageContent` вместо новой сущности избыточно: `PageContent.TextContent` ограничен 2000 символами и модель "один ключ — одно текстовое поле" не годится для структурированных блоков (массив FAQ, массив цен, ссылки на конкретные работы по категории). Правильное решение — новая сущность `LandingPage`, но **не по одной таблице на страницу**, а один универсальный тип с типизированными полями под весь набор блоков, чтобы 4 страницы не превращались в 4 разных контроллера.

`backend/MomSite.Core/Models/LandingPage.cs`:

```csharp
public class LandingPage
{
    public int Id { get; set; }

    [Required, MaxLength(100)]
    public string Slug { get; set; } = string.Empty; // "kupit-kartinu" | "zakazat-portret" | "natyurmorty" | "peyzazhi"

    [Required, MaxLength(50)]
    public string PageType { get; set; } = string.Empty; // "gallery-commercial" | "portrait-commercial" — определяет, какие блоки рендерить (наличие "Процесс заказа")

    [Required, MaxLength(300)] public string MetaTitle { get; set; } = string.Empty;
    [Required, MaxLength(500)] public string MetaDescription { get; set; } = string.Empty;
    [Required, MaxLength(200)] public string H1 { get; set; } = string.Empty;
    [MaxLength(500)] public string? HeroSubtitle { get; set; }
    [MaxLength(500)] public string? HeroImagePath { get; set; }

    public string? TrustBlockHtml { get; set; } // короткий блок доверия, редактируется отдельно от about, чтобы не тянуть всю биографию
    public string? ProcessStepsJson { get; set; } // JSON-массив { title, description } — этапы заказа, null для не-портретных страниц
    public string? FaqJson { get; set; } // JSON-массив { question, answer }
    public string? ReviewsHtml { get; set; }

    public int? FilterCategoryId { get; set; } // Category.Id для блока "Примеры работ"; null => IsForSale-фильтр без категории (для /kupit-kartinu)
    public string? PriceRangeOverrideText { get; set; } // если нужно переопределить авторасчёт вилки цен вручную

    public bool IsPublished { get; set; } = true;
    public DateTime UpdatedAt { get; set; } = DateTime.UtcNow;
}
```

`ProcessStepsJson`/`FaqJson` — сериализованный JSON внутри `text`/`nvarchar(max)` колонки, а не отдельные таблицы: это ограниченный, редко меняющийся набор из 4-6 элементов на 4 страницы, отдельная связная таблица (как `BlogPostArtwork` в блоге) была бы оверинжинирингом. В админке эти поля редактируются как динамический список полей "вопрос/ответ" на клиенте, а на сервер уходит уже готовый JSON-массив.

Эндпоинты `PublicController`:
```csharp
[HttpGet("landing/{slug}")]
public async Task<ActionResult<LandingPageData>> GetLandingPage(string slug)
```
Внутри — подтягивает `LandingPage` по `slug`, затем работы: `_context.Artworks.Where(a => a.CategoryId == landing.FilterCategoryId && a.IsForSale)` либо, если `FilterCategoryId == null`, топ работ по `IsForSale` без фильтра категории; вычисляет `PriceRange = (Min, Max)` по выборке, если `PriceRangeOverrideText` не задан.

Админка: `backend/MomSite.API/Controllers/Admin/LandingPagesController.cs` (CRUD по 4 записям, без возможности создавать произвольные новые — список из 4 slug фиксирован в UI, но модель не запрещает добавить пятую страницу в будущем), фронтенд `frontend/app/admin/landing-pages/page.tsx` со списком из 4 карточек и формой на каждую, включая динамические списки для FAQ и этапов заказа и выбор `FilterCategoryId` из существующего справочника категорий.

Next.js-маршрутизация: `frontend/app/(landing)/kupit-kartinu/page.tsx`, `.../zakazat-portret/page.tsx`, `.../natyurmorty/page.tsx`, `.../peyzazhi/page.tsx` — четыре физических роута (не один динамический `[slug]`), потому что это ограниченный список страниц с разным типом content (`pageType` управляет составом блоков, но конкретная верстка/акценты у "купить" и "заказать портрет" всё равно расходятся сильнее, чем у блога, где все статьи однородны). Каждая страница — серверный компонент, получает данные через `getLandingPage(slug)` в `hooks/useApi.ts`, `dynamic = 'force-dynamic'` или `revalidate = 3600` по аналогии с `/gallery`.

## 4. Schema.org и перелинковка

| Страница | Основная разметка | Дополнительно |
|---|---|---|
| `/kupit-kartinu` | `Product`/`ItemList` (для набора картин на продажу) с `offers: AggregateOffer` (`lowPrice`/`highPrice` из вычисленной вилки) | `BreadcrumbList`, `FAQPage` |
| `/zakazat-portret` | `Service` (`serviceType: "Портрет на заказ"`, `provider: Person`) | `BreadcrumbList`, `FAQPage`, `HowTo` для этапов заказа (опционально, если `ProcessStepsJson` заполнен) |
| `/natyurmorty`, `/peyzazhi` | `Product`/`ItemList` с `AggregateOffer`, аналогично `/kupit-kartinu`, но с `itemListElement`, отфильтрованным по категории | `BreadcrumbList`, `FAQPage` |

`FAQPage` строится из `FaqJson` напрямую — по образцу того, как `ContactsData.FAQ` уже собирается в `PublicController.GetContactsData()` (4 вопроса из `PageContent`), только источник данных — `LandingPage.FaqJson`, а не отдельные ключи.

Перелинковка:
- Каждая посадочная → `/gallery?category={id}` ("смотреть все работы этой категории") и к отдельным `/gallery?artwork=N` из блока примеров.
- Каждая посадочная → релевантные статьи блога (рубрика `istorii`/`tehniki`/`portret`) через блок "Читайте также" — по 2-3 статьи с `Category`, соответствующей типу страницы (см. `docs/blog-plan.md`, таблица рубрик уже указывает целевую посадочную для каждой рубрики — связь обратная и должна быть отражена на обеих сторонах).
- Из `/gallery` (шапка/подвал категории) и из карточки категории в галерее — ссылка на соответствующую посадочную, если она существует для этой категории (жёстко прописать 4 соответствия в конфиге фронтенда: `categorySlugToLanding: { 'natyurmorty': '/natyurmorty', 'peyzazhi': '/peyzazhi' }`).
- Из статей блога — CTA-блок в конце ведёт на посадочную (уже описано в `docs/blog-plan.md`, п.3.4).

## 5. Риски и как их избежать

| Риск | Механизм | Как избежать |
|---|---|---|
| Дубль с `/gallery` и категориями | Посадочная и `/gallery?category=N` показывают частично одинаковые работы | Посадочная показывает только 6-9 отобранных карточек как витрину, `canonical` посадочной указывает на саму себя (не на `/gallery`), а текстовый контент (доверие, процесс, FAQ, вилка цен) на `/gallery` отсутствует — страницы не идентичны по контенту, что снимает риск дубля для поисковика |
| Каннибализация запросов | `/kupit-kartinu` и `/natyurmorty`/`/peyzazhi` конкурируют за смежные запросы типа "купить картину пейзаж" | Явное распределение семантики: `/kupit-kartinu` — общие/подарочные запросы и запросы без указания жанра, `/natyurmorty`/`/peyzazhi` — жанровые запросы; внутренняя перелинковка (п.4) явно сигнализирует поисковику иерархию через `BreadcrumbList` и ссылки "смотреть все пейзажи" именно с `/kupit-kartinu` на `/peyzazhi`, а не наоборот |
| Тонкий контент | Голая посадочная с одной галереей карточек и без уникального текста хуже ранжируется, чем `/gallery`, и не конвертирует | Обязательные текстовые блоки out of the box: доверие, вилка цен, FAQ (минимум 4 вопроса), для портрета — процесс. Публикация страницы без заполненных `FaqJson`/`TrustBlockHtml` в админке должна быть возможна технически, но перед реальным запуском в поиск (что фиксируется через `IsPublished` + отсутствие в `sitemap.ts` до заполнения) — так тонкий контент не индексируется преждевременно |

## 6. Порядок запуска

1. **`/kupit-kartinu`** — первым, потому что это самый широкий и самый частотный кластер запросов, закрывает общий "вход" в коммерческую воронку и снимает наибольший текущий пробел (аудит показал: нет ни одной страницы с коммерческим title/H1 в принципе).
2. **`/zakazat-portret`** — вторым: отдельный тип услуги с максимальной маржой и наибольшим разрывом между спросом ("заказать портрет" — устойчивый частотный запрос) и текущим предложением (портрет вообще нигде не выделен на сайте как услуга).
3. **`/natyurmorty`** и **`/peyzazhi`** — третьими, парой: более узкие жанровые кластеры, имеет смысл выпускать после того, как отработана и провалидирована по конверсии структура блоков на первых двух страницах (меньше повторной переделки).

Каждая следующая страница переиспользует уже готовый рендер-каркас (`LandingPage`-модель, эндпоинт, компонент блоков) — после первой страницы стоимость каждой следующей это в основном заполнение контента через админку, а не разработка.
