### Risk 2 — `AssemblyInfo.cs` disabling test parallelization
Verified the stated justification is real: temporarily removed `AssemblyInfo.cs` and reran the suite —
```
Failed!  - Failed: 4, Passed: 117, Total: 121, Duration: 1s
  MessageEndpoint_WithValidToken_ReturnsSuccess(...) → 401 (flaky, env-var race between
  AdminMessagesAuthorizationIntegrationTests and AdminReviewsControllerTests fixtures)
```
Restored the file immediately after (working tree confirmed clean, no accidental commit).

Only **two** test classes touch process-wide env vars (`JWT__Secret`, `AdminPassword`): `AdminMessagesAuthorizationIntegrationTests` and `AdminReviewsControllerTests` (`grep -rl SetEnvironmentVariable backend/MomSite.Tests/*.cs`). A narrower fix is obviously applicable: put both classes in a single shared xUnit collection (`[CollectionDefinition("AdminEnvIntegration")]` + `[Collection("AdminEnvIntegration")]` on each class) instead of `[assembly: CollectionBehavior(DisableTestParallelization = true)]`. This serializes only the two classes that actually race, while leaving the other ~115 tests (unit tests, other controller tests) free to run in parallel. The measured wall-clock cost of the current broad fix is small (~1–2s on this 121-test suite) but it scales badly and is unnecessary collateral restriction as the suite grows — the assembly-wide attribute silently serializes every future test class too.

**Verdict: narrow fix is obvious and low-effort → this is the basis for `send-back`.**
